# Grok authentication and isolation audit

Checked 2026-10-28. Source observations below are pinned to official `xai-org/grok-build` commit `2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8`. The separately probed binary identifies itself as `1.0.70 (f50904eaee6c)`; this audit does not claim those revisions are identical.

## Earlier authentication investigation

The initial empty-home probe advertised only `grok.com`. That does not contradict the documented `cached_token` example. [Auth method construction](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/auth_method.rs) includes cached-token authentication only when a cached credential is available. Hovel's parser now distinguishes a cached credential path, API-key availability, a signed-out method list and unknown methods. None means verified subscription readiness.

The remaining concern is fallback. [Cached-token failure handling](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/mvp_agent/agent_ops.rs#L1465) can fall through to another method when no auth family is pinned. Its `grok.com` branch replaces the request metadata, so merely passing `headless: true` is not a sufficient no-login guarantee. The working adapter must not assume authentication on an unpinned player configuration is safe. The chat solution below pins its own disposable configuration.

## Isolation evidence

- The [config overlay allowlist](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-config/src/config_override.rs) permits selected model/features/tool/environment settings. It does not permit replacing auth, hooks, plugins or MCP configuration wholesale. An empty overlay is not a clean configuration.
- The [headless tool controls](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/14-headless-mode.md) preserve MCP meta-tools after the tool allowlist. A short or empty allowlist alone does not establish tool-free talk.
- [Agent definition validation](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/builder.rs) rejects a curated definition with an empty tool list. A custom empty profile is not an established solution either.

These are specific gaps in the investigated controls, not a claim that no supported configuration can exist. Do not change the player's persistent config or copy credentials to work around them.

## Observed binary behavior

Both Python and the native `GrokAcpSmokeTest` successfully initialized the official binary in a disposable home. The native test then called `session/new` with client filesystem/terminal capabilities disabled and `mcpServers: []`; it received `-32000` without an auth request or prompt.

The [controlled startup probe](startup-1.0.70.json) added one temporary MCP entry whose command could only touch a marker in the temporary directory. `grok inspect --json` still reported that entry with `--tools ''`, `--no-subagents`, `--disable-web-search` and compatibility scanners disabled. Initialize succeeded; session creation was rejected; the marker was absent. This proves discovery retained the configuration. It does **not** prove authenticated initialization or session startup would suppress it.

The first pass used only a temporary binary. After the user installed and signed in to Grok Build, the installed `~/.grok/bin/grok` reported version 1.0.70 and advertised `cached_token` plus `grok.com` through initialization. Both the bounded diagnostic and production status reader observed this without calling authentication, creating a session or sending a prompt. The card now recognizes this saved sign-in. Entitlement/model, auth-expiry, session startup, resume, permissions and cancellation acceptance remain open.

The pinned [ACP initialization implementation](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/mvp_agent/acp_agent.rs) derives advertised methods from the runtime's credential state and may silently refresh expired credentials. Its launch MCP setup loads configuration; plugin registry/session creation are separate. The earlier detection-only status reader called only initialization, refuses incoming client requests, disables compatibility discovery, uses a private temporary working folder, and closes the process after reading the bounded auth vocabulary. It does not invoke the unsafe authentication fallback described above. This is not a general session isolation guarantee.

## Permission mapping evidence

The native permission code follows [ACP v1 permission outcomes](https://agentclientprotocol.com/protocol/v1/tool-calls): retain opaque option IDs, select only the unambiguous allow/reject-once pair and return cancellation when the turn ends. Persistent options never become Hovel conversation grants.

Structured operation descriptions are derived from the pinned source's [published tool metadata schema](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/schema/tool_meta.schema.json), [normalization implementation](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/normalization.rs), and permission stamping in `session/acp_session_impl/tool_calls.rs`. Version 1 metadata supplies tool identity and canonical input; full edit/write text comes from `rawInput`. Hovel checks agreement before constructing its existing native approval subject. It does not approve from an agent-authored title.

The initial subset covers `grok_build` execute/search-replace and `opencode` write. Full payloads must fit the current native preview. Unknown fields/shapes, connectors, other toolsets, inconsistent metadata and explicitly requested background execution are denied. Default runtime behavior can still detach work, so this decoder is not a cancellation guarantee. The initial metadata fixtures were source-derived and the relay-to-transport test used a fake process/controlled broker. Subsequent authenticated command/edit and native-dialog checks are recorded below and in the work evidence file.

## Verified authenticated chat controls

The 1.0.70 binary passed the production `GrokConnection` and `GrokChatRuntime` checks recorded in [talk evidence](talk-1.0.70.json). The supported `GROK_AUTH_PATH` setting points the isolated process at the original runtime-owned credential store; Hovel neither opens nor copies that file. A fresh private HOME/GROK_HOME pins `[auth] preferred_method="oidc"`. A live empty-store check returns `-32000` for cached authentication without requesting client interaction. Personal OIDC subscription metadata, an explicit null access gate and a stable identity fingerprint are required. The runtime owns refresh and may use valid cached metadata; no independent billing freshness claim is made.

The [profile builder](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/builder.rs) validates the initial curated list before applying its denylist. The accepted profile declares `GrokBuild:read_file` then denies `read_file`, `search_tool`, `use_tool` and `Agent`. It disables default-tool injection, skills discovery/inheritance, AGENTS.md and MCP inheritance. This is supported configuration, not a modified runtime. The binary reports effective `tools: []` in the exact session's `available_commands_update`; every later toolset update is also checked. A nonempty/missing toolset or tool activity closes the turn.

The [skill configuration](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/prompt/skills.rs) supports path-prefix exclusions. `[skills] ignore=["/"]` excludes all absolute skill paths in the isolated macOS process, including bundles downloaded after login. A live fixture placed a skill on disk and verified that `inspect --json` still reported no skills. This also closes the reload path, which otherwise refreshes skills independently of the profile's startup discovery flag.

The [stdio watcher](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/agent/app.rs) injects `skills-reload` and `workflows-reload` requests into the shared incoming stream. Their [handlers](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-shell/src/extensions/session_admin.rs) return `{result:{reloaded:N}}` inside the JSON-RPC result. A live trace confirmed `skills-reload` and this nested result envelope. Hovel accepts only those exact successful internal frames with a bounded session count, only after version/config verification. Unknown string IDs, malformed replies, numeric-string substitutions and unopted-in watcher frames still fail closed. These replies never complete a Hovel request.

Persisting a whole Grok home was rejected after the real restart test discovered downloaded bundles on the next launch. Each process now has fresh configuration; only the runtime's session directory is linked to private persistent data. Restart/resume retains context. Process teardown precedes temporary-file deletion, which never follows the session-data link. This keeps later preference changes and downloaded startup content from changing the next process's launch policy.

## Approved local work configuration

The inspected CLI help has no per-process auth-family argument, and the supported config overlay excludes auth. Work must preserve configuration and project rules, so chat's isolated config cannot simply become the work launcher. Work therefore requires the player to add `[auth] preferred_method="oidc"` to their own Grok config, which also affects Grok outside Hovel; see the [player requirement](README.md#player-requirement-for-work). The acceptance installation added it with every other setting preserved. This is a player prerequisite, not an automatic configuration migration performed by Hovel.

`GrokWorkAuthSmokeTest` passed real subscription authentication/session creation and empty-store authentication rejection with the original HOME/GROK_HOME. No model prompt or client request was sent in those two checks. Both confirmed byte-for-byte config preservation. The preflight retained user skills/project instructions and required no hooks/plugins/MCP/LSP or managed settings before the bounded probe. Other configuration combinations remain unverified. The live command/edit permission, native dialog, activity and detached-work cancellation checks are separate requirements.

The subsequent controlled work turns found `rawInput.variant` in real permission payloads. The [tagged ToolInput enum](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-tools/src/types/tool_io.rs#L55) defines `Bash`, `SearchReplace` and `Write`. The native decoder now permits that field only when it matches the canonical operation; a mismatched/null/unknown variant still denies. Real command and search-replace tests each allowed one exact temporary operation, reset the fixture, repeated the operation explicitly, observed a fresh permission request and denied it without changing the file. A denial may end the prompt with `cancelled`.

A foreground command with a controlled sleep was observed running, cancelled with a terminal response within five seconds, and reaped with its observed descendants on process teardown. This does not establish cleanup for implicit detachment or remote tasks, pending native dialogs, close or profile changes. [Sanitized work evidence](work-1.0.70.json) records the scope. That earlier protocol-only stage has been superseded by the work-runtime continuation below.


## Work runtime, persistent trust and foreground execution

The development `GrokWorkRuntime` now uses the original provider home for ordinary work, with a private per-turn profile and no client filesystem/terminal capabilities. It requires parsed `[auth] preferred_method="oidc"`, the exact binary version, one user configuration layer, and empty hooks/plugins/MCP/LSP/managed-policy discovery. Endpoint/model-provider overrides and Bash command prefixes are rejected. It preserves discovered skills and project instructions; it does not claim support for additional configuration layers.

Grok's [folder trust resolver](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/folder_trust.rs) can omit project instructions from an untrusted folder even after an individual tool edit is approved. Inspection exposes `projectRoot` and `projectTrusted`. Hovel asks a separate native question naming that root, explains persistence outside Hovel, and invokes the runtime's `--trust inspect --json` only after confirmation. The returned configuration is revalidated, and again before prompting. The trust acceptance tests use a disposable provider configuration home with a reference to the original credential store; no credential is copied and the real user's trust store is unchanged by those tests.

In the audited [agent builder](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-agent/src/builder.rs), profile tool parameters are merged before the final subagent restriction. A nonempty allowlist with no Agent directives resolves to an empty allowed-subagent set and forces Bash `enabled_background=false` and `auto_background_on_timeout=false` after those merges. Hovel's profile also disables `allow_background_operator` and restricts tools to read/list/search/search-replace/terminal-command. These controls, not just a prompt instruction or an initial parameter default, underpin foreground execution on this version.

The real production-adapter cleanup test kept a shell/sleep command foreground for 35 seconds without an explicit blocking/timeout/background parameter, then stopped it. Stop, release and close each reaped the observed shell/child, and the final write did not run. Native UI checks additionally exercise actual dialogs and the app's Stop path. Arbitrary self-detaching commands, remote jobs, other runtime versions and unaccepted configurations remain outside this evidence. See [sanitized work evidence](work-1.0.70.json).
